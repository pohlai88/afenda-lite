## Package README

`@afenda/master-data` is the Rank-1 ERP operational-master package for Afenda-Lite.

It owns ERP-facing read/query helpers for platform `ref_*` lookups plus domain commands, queries, Zod brands, lifecycle transitions, version CAS, import/change-request flows, merge policy, and search projection hooks for organization-scoped `md_*` masters. Outcomes use `@afenda/errors` `Result`; adapters map those results to HTTP, Server Actions, or UI state outside this package.

Use this package from Platform and app server code when creating or mutating organization dimensions, parties, items, item groups, warehouses, payment terms, tax registrations, item templates, variants, and their extensions. Maintainers run lint, typecheck, and Vitest through the package filter scripts below.

**Tables live in `@afenda/db`.** Organization-scoped master-data mutations are sole-owned here — do not dual-write `md_*` from `apps/web` or transactional modules. Platform `ref_*` rows are read-only to this package.

**UoM is platform-only:** `ref_uom_dimension` → `ref_uom`; `md_item.base_uom_id` → `ref_uom`; item packaging conversions in `md_item_uom`. There is no org-scoped `md_uom`.

## Store / ports

| Surface | Backend |
|---------|---------|
| Production default | `DrizzleMasterDataStore` (`@afenda/master-data/adapters/drizzle`) → `@afenda/db` — every org mutation must run in one database transaction that atomically persists the authoritative state change, `platform_audit_log`, and `platform_domain_event` |
| Vitest injection | `MemoryMasterDataStore` + memory `AuditFactPort` / `OutboxPort` (in-process atomic) |
| `MutationPorts` | **Memory/test composition only.** Production atomicity is the store transaction contract. Do not wrap Drizzle in fake port calls. |

Simple production mutations should use the standard `runNeonHttpTransaction` CTE pattern. Complex workflows may use an approved equivalent transaction implementation when they require multiple statements, row locking, staging, dependent inserts, bulk chunks, or recursive merge checks.

Standard production mutation sequence:

1. authorize command
2. parse and normalize input
3. begin authoritative mutation transaction
4. load target under tenant scope
5. verify expected version
6. verify lifecycle and business invariants
7. mutate entity
8. insert audit fact
9. insert domain event/outbox record
10. commit
11. return `Result`
12. asynchronously project search

Application layers must never sequence `store.update*`, `audit.write`, and `outbox.publish` as separate awaits. A failed audit or outbox write after an entity write would corrupt the authoritative evidence trail. Production stores persist state, audit, and outbox atomically; memory stores simulate this with rollback snapshots.

Version-CAS is mandatory for mutable authoritative `md_*` records. Mutable master rows carry `version`, `created_at`, `created_by`, `updated_at`, and `updated_by`; successful updates increment `version` exactly once and stamp `updated_at`/`updated_by` in the same transaction as audit and outbox writes. Production updates must scope by `organization_id`, `id`, and `expectedVersion` in the authoritative write predicate.

When a CAS update returns zero rows, the store must run a tenant-scoped probe before choosing the error: no row in the caller organization returns tenant-safe not-found; a row with a different version returns `MASTER_DATA_VERSION_CONFLICT`; a same-version row means another invariant guard failed and returns invalid state/dependency evidence. Stores must not query by ID outside organization scope to explain cross-organization misses.

Lifecycle policy is centralized under `src/capabilities/lifecycle-governance`. New aggregates must bind to one shared family and must not invent unrelated status sets.

| Family | Canonical states |
|--------|------------------|
| Simple reference-like master | `draft` · `active` · `inactive` · `archived` |

The database still contains older persisted names for several master records. The package maps them through `toStandardLifecycleState`: `inactive` and `blocked` are operational `suspended`; `retired`, `archived`, and `merged` are operational `archived`; effective-dated `draft` and `inactive` are `pending`; governance `applying` is treated as `approved`, while `expired` and `superseded` are terminal `cancelled` outcomes.

Every lifecycle transition must declare allowed source states, target state, required permission, reason policy, CAS requirement, emitted event, audit action, reversibility, parent/dependency evidence, and search-projection consequence. `defineLifecyclePolicy` supplies the default lifecycle audit action `UPDATE`; transitions that need another audit action must set it explicitly.

## MD-1 Platform References and Organization Dimensions

Platform reference rows are global and read-only, but application access uses the root organization-authorized facade: `getRefCountryByCode`, `getRefCurrencyByCode`, `getRefLanguageByCode`, `getRefTimeZoneByIana`, `getRefUomDimensionByCode`, `getRefUomById`, `getRefUomByCode`, and `listRefUoms`. These operations require an explicit organization/actor context and `master_data.reference_read`. Injected store queries, active-reference policies, and reference error helpers remain internal implementation capabilities rather than a second consumer API.

Organization dimensions are hard-tenant operational masters. The controlled taxonomy is:

`legal_entity` · `business_unit` · `location` · `department` · `cost_center` · `cost_centre` · `profit_center` · `channel` · `region` · `brand` · `project` · `custom`

Supported commands and queries: create, update, activate, deactivate, archive, get by ID, get by code, list, and effective-date resolution. Updates and lifecycle transitions require `expectedVersion`. Uniqueness is enforced by organization, dimension kind, normalized key, and effective version range.

Hierarchy rules are conservative: no self-parenting, no ancestor cycles, no cross-organization parent references, and inactive or archived parents cannot receive new children or reparented children. Archived nodes remain resolvable through historical/effective lookups.

## MD-2 Party Master

Party is the primary master aggregate. Public MD-2 command names are exposed as:

`createParty` · `updateParty` · `activateParty` · `suspendParty` · `archiveParty` · `restoreParty`

The storage lifecycle remains the existing canonical status set: `draft`, `active`, `inactive`, `blocked`, and `retired`. MD-2 naming maps `suspendParty` to `blocked` and `archiveParty` to `retired`; consumers should use the command names for intent and the stored status for persisted state.

Supported queries are:

`getParty` · `getPartyByCode` · `listParties` · `searchParties`

Party activation requires at least one active role and an approved `activate_party` change request. Deactivating or archiving the final active role of an active party is rejected; an explicit party suspension must happen through a governed party command.

Party roles use a controlled catalog, not arbitrary strings:

`customer` · `supplier` · `employee` · `contact` · `carrier` · `bank` · `tax_authority` · `government_agency` · `franchisee` · `franchisor` · `manufacturer` · `distributor` · `retailer` · `service_provider` · `landlord` · `tenant` · `other`

Existing role values `agent`, `regulator`, and `other_authorized_role` remain supported for compatibility.

Addresses carry type, purpose, country, postal fields, effective dates, primary flag, validation status, and lifecycle. Contacts carry contact type, value, label, purpose, verification status, primary flag, communication preference, consent status, effective dates, and lifecycle. Primary records are scoped by party and purpose/type; replacement of a primary record is atomic in the store.

Party external IDs are unique by organization, source system, external ID type, normalized value, and case-sensitivity mode. Relationships store one canonical row with source party, target party, relationship type, directionality, effective dates, and lifecycle. Reciprocal and symmetric reads are derived from the relationship policy; commands do not store duplicate inverse rows.

## MD-3 Item and Item-Group Master

Item groups are hierarchical operational masters. They support create, update, activate, inactive, retire, list, code lookup, ID lookup, and deterministic path resolution through `resolveItemGroupPath`. Parent assignment is tenant-scoped and rejects self-parenting, ancestor cycles, inactive parents, retired parents, and cross-organization parents. Live item-group codes are unique per organization.

Each item belongs to exactly one primary `md_item_group` through `md_item.item_group_id`. Multiple merchandising/accounting group assignments are not modeled in MD-3; add a governed extension table before supporting secondary group memberships.

Item core commands are:

`createItem` · `updateItem` · `activateItem` · `suspendItem` · `archiveItem` · `restoreItem`

The storage lifecycle remains `draft`, `active`, `inactive`, and `retired` for items. MD-3 naming maps `suspendItem` to `inactive` and `archiveItem` to `retired`; `restoreItem` moves `retired` back to `draft` through the restore lifecycle policy.

Core item fields are code, name, description, item type, single item group, base UoM, tracking policy, sellable, purchasable, stocked, service indicator, status, and version. `itemType` remains controlled by `ITEM_TYPES`; `trackingPolicy` remains controlled by `ITEM_TRACKING_POLICIES`. Stock quantities, selling price history, purchase price history, BOM, ledger balances, and warehouse balances are outside master-data and belong to inventory, commercial, manufacturing, accounting, or transactional packages.

Item UoM conversions use canonical direction:

`1 alternate UoM = conversionFactor x item base UoM`

The item base UoM must exist in `ref_uom`; `createItem` writes the base conversion row with factor `1`. Alternate conversions must reference active platform UoMs, use a positive factor, remain within the same UoM dimension unless an explicitly approved packaging/count mode is used, and stay unique per active item/UoM. Commands reject explicit alternate rows for the item base UoM to avoid conflicting forward/reverse representations.

Barcodes are normalized by symbology and unique by organization, symbology, and normalized value while active. A primary barcode is scoped by organization, item, and optional packaging UoM. Barcode packaging UoM must either be the item base UoM or an existing active item conversion.

Aliases are discovery labels, not second item identities. They carry controlled alias type, optional language, normalized alias value, source, searchable flag, lifecycle, and version. Active alias identity is scoped by organization, item, alias type, language, and normalized value.

Item external IDs are unique by organization, source system, external ID type, normalized value, and case-sensitivity mode while active. Primary external IDs are scoped by organization, item, source system, and external ID type.

## MD-4 Warehouse, Payment, and Tax Masters

Warehouse identity belongs to master-data: code, name, warehouse type (`locationType`), parent association, postal address association, lifecycle, version, and external IDs. Live warehouse codes are unique per organization. Internal bins, zones, putaway topology, stock statuses, capacity operations, and warehouse execution workflows belong to inventory or a warehouse-management package; downstream modules reference `warehouseId` and do not mutate warehouse masters.

Warehouse lifecycle intent names are exposed as `activateWarehouse`, `suspendWarehouse`, and `archiveWarehouse`. The stored status enum remains `active`, `inactive`, and `retired`; `suspendWarehouse` maps to `inactive`, and `archiveWarehouse` maps to `retired`.

Payment terms use a structured commercial rule model: `netDays`, optional early-payment discount days/percent, due-day rule, end-of-month flag, installment policy/count, effective dates, and optional currency restriction. This is not a universal payment engine; sales and purchasing should snapshot the selected term and calculate due dates in their own transaction context.

Tax registrations are unique while live by organization, party, country, tax type, and normalized registration number. Commands store the existing canonical status set, while lifecycle evaluation exposes `pending_verification`, `active`, `expired`, `revoked`, and `archived`: `draft`/other non-active states project to `pending_verification`, active rows with `validUntil < asOf` project to `expired`, `blocked` projects to `revoked`, and `retired` projects to `archived`. Public commands and ordinary queries return `TaxRegistrationProjection`; raw registration numbers are available only through dedicated sensitive queries.

Cross-module contract: sales references party, party role, item, payment term, and warehouse IDs; purchasing references supplier role, item, payment term, and warehouse IDs; inventory references item and warehouse IDs; accounting references dimensions and tax registrations where appropriate. Package tests prevent downstream ERP modules from importing master-data mutation commands or directly mutating `md_*` master tables.

## MD-5 Templates and Variants

Item templates are enforceable product-family schemas with optimistic versioning. They are not loose authoring helpers and not immutable family definitions. Template update and lifecycle commands require `expectedVersion`; schema shape is mutable only while the template is `draft`. Public commands are `createItemTemplate`, `updateItemTemplate`, `activateItemTemplate`, and `archiveItemTemplate` (`archiveItemTemplate` maps to the stored `retired` status).

Template attributes define code, name, data type, required flag, variant-defining flag, searchable flag, display order, and typed validation rules. Supported data types are explicit: `text`, `integer`, `decimal`, `boolean`, `date`, `single_option`, `multiple_option`, and `reference`. Variant values are stored in typed columns, not as unvalidated strings or a JSON bag.

The permanent contract uses `dataType`, `displayOrder`, and `textValue`. Historical `valueKind`, `sortOrder`, and `valueText` inputs are accepted only by the schema ingress boundary, normalized immediately, and never returned by domain records. Consumers must not reconstruct the removed lossy `text | option` projection or use the retired `listTemplateAttributes` / `listTemplateAttributeOptions` aliases.

Attribute options belong to exactly one option-compatible attribute. Active option codes are unique per attribute by normalized code. Archived options cannot be assigned to new variants; historical assignments remain readable through variant configuration queries.

Variant creation validates that the template is active, all required attributes are supplied, no unknown attributes are supplied, each supplied value matches the attribute data type/rules, options belong to the correct attribute, archived options are rejected for new assignments, and the variant-defining combination is unique while live.

Every variant creates and references an `md_item`; `md_item` remains the operational SKU authority for sellable, purchasable, stocked, or independently referenced variants. `md_item_template` and `md_item_variant` define product-family configuration and variant membership, while transactional modules reference the `md_item` SKU identity.

## MD-6 Import Lifecycle, Policy, and Recovery

Import batches use this bounded lifecycle:

```text
parsed
validated
approval_pending
approved
applying
partially_applied
applied
failed
cancelled
```

Each returned row-level import result carries source row number, raw payload, normalized payload, matched target ID, intended operation, validation errors, application result, and resulting entity ID/version when a master record is created, updated, replayed, or otherwise resolved.

Supported modes are `create_only`, `update_existing`, and `create_or_update`. Automatic matching is deterministic only: primary match is normalized master code; optional secondary match is an approved external identifier. Fuzzy name, address, phone, or similarity matching may create warnings or review candidates, but must never automatically choose update targets or mutate records.

Imports are bounded execution workflows. Callers must enforce row and payload-size limits, preserve an immutable source snapshot, pass actor and correlation context, validate with dry-run before approval, apply with an idempotency key, process rows or chunks atomically instead of one massive transaction, report partial failures, and allow failed rows to be retried without replaying already-applied rows.

## MD-7 Duplicate, Merge, Search, and Observability

Duplicate warnings are advisory evidence unless a deterministic unique key is violated. Detection may use normalized name, tax registration, external IDs, email, phone, address, item barcode, and aliases, but warnings must not auto-merge or auto-update masters. Stored warning evidence includes canonical candidate pair, match reasons, score, detection timestamp, review status, reviewer, and resolution.

Party merge requires an approved change request, same-organization source and target, distinct parties, current source and target versions, compatible lifecycle states, no existing source merge, no target merged into another party, canonical target selection, explicit duplicate/manual reason evidence, and recorded conflict decisions. Merge effects mark the source non-operational with `merged_into_id`; reads may resolve the canonical party through `resolveCanonicalPartyId`. Historical records retain the originally recorded source party ID, query projections may resolve to the canonical target, and financial/legal documents must preserve the original recorded identity.

Search projection is asynchronous, idempotent, version-aware, replayable, organization-scoped, and rebuildable by entity type and organization. Rebuild coverage includes parties, items, warehouses, organization dimensions, item groups, and payment terms. Tax registrations are not generally projected because registration numbers may be sensitive; use masked, permissioned tax-registration queries instead unless a restricted projection policy is explicitly introduced.

Every production mutation must prove the state change, audit fact, and domain event share the same organization, actor, correlation ID, entity ID, and resulting version. Event contracts are specific per aggregate and operation, including organization-dimension created/updated, party created/activated/suspended/merged, party-role activated, item created/activated, warehouse created, change-request approved/applied, and import-batch approved/applied.

## Search and merge boundaries

| Concern | Rule |
|---------|------|
| Search projectors | Master mutation commits authoritative data, audit, and outbox atomically; search projection is asynchronous, idempotent, and non-authoritative |
| Search failure | Search failure never rolls back an already committed master mutation; commands may succeed while search is stale |
| Search authority | Authorization is always derived from master-data authority, not search documents; search never mutates masters |
| Search recovery | Rebuild-from-SSOT is required for recovery; search documents carry `organizationId`, entity type, entity ID, version, and `projectedAt` |
| Direct search writes | Allowed only as explicit non-authoritative best-effort optimizations after master writes |
| Merge | `mergeParties` is MDG-gated (approved change request); no peer-table rewrite; source gets `merged_into_id` |
| Change requests | MDG v1 gates `activate_party` and `merge_parties`; future coverage must stay limited to controlled master-data changes, not a generic workflow engine |
| Import modes | `create_only` · `update_existing` · `create_or_update` (default) + mutable-field allowlist; validate requires `master_data.import_validate`; apply requires `approved` + `master_data.import_apply`; approval remains `master_data.import_approve`; `requireSegregatedApproval` can require `actorUserId != approvedByActorUserId` |

## Code policy

Master-code fields use `normalizeMasterCode()`: trim, Unicode NFC, uppercase comparison value, then ASCII charset validation. Max length is 64. Charset after uppercase fold is `[A-Z0-9._-]`.

Apply that rule consistently to identifier-like master codes: party, item, warehouse, item group, organization dimension, item template, item variant, template attribute, template option, and any external-source/provenance code that is modeled as a master code. The collision model is explicit: values such as `" acmé "` normalize to `"ACMÉ"` and then fail because `É` is outside the declared ASCII charset. The package does not transliterate or silently collapse non-ASCII codes.

Do not reuse master-code normalization for human-search or externally assigned identifiers:

| Helper | Contract |
|--------|----------|
| `normalizeMasterCode()` | Organization-owned identity code, uppercase ASCII comparison |
| `normalizeSearchText()` | Human search text, NFC display value, whitespace collapse, NFKC lowercase comparison |
| `normalizeEmail()` | Contact email, preserve display casing, lowercase domain in comparison |
| `normalizePhone()` | Contact phone, canonical international `+` digits comparison |
| `normalizeBarcode()` | Item barcode, symbology-specific normalization and checksum validation |
| `normalizeExternalId()` / `normalizeExternalIdValue()` | External ID values preserve case when the external source is case-sensitive; only case-insensitive identities uppercase their comparison value |

External-ID `sourceSystem` and `externalIdType` qualifiers remain lower-case `[a-z0-9._-]` to match the existing database contract. They are qualifiers for externally assigned IDs, not organization-owned `normalized_code` fields.

## Result and Error Taxonomy

Package functions return `@afenda/errors` `Result<T>`. `Result.code` stays transport-neutral (`BAD_REQUEST`, `NOT_FOUND`, `CONFLICT`, `FORBIDDEN`, and so on). Master-data domain failures normalize to the stable `MasterDataErrorCode` taxonomy exported from `@afenda/master-data`.

Canonical MD-0.2 codes:

`MASTER_DATA_INVALID_INPUT` · `MASTER_DATA_NOT_FOUND` · `MASTER_DATA_ALREADY_EXISTS` · `MASTER_DATA_VERSION_CONFLICT` · `MASTER_DATA_INVALID_STATE` · `MASTER_DATA_CODE_CONFLICT` · `MASTER_DATA_EXTERNAL_ID_CONFLICT` · `MASTER_DATA_CROSS_ORGANIZATION_ACCESS` · `MASTER_DATA_PERMISSION_DENIED` · `MASTER_DATA_REFERENCE_NOT_FOUND` · `MASTER_DATA_DEPENDENCY_EXISTS` · `MASTER_DATA_DUPLICATE_CANDIDATE` · `MASTER_DATA_CHANGE_REQUEST_REQUIRED` · `MASTER_DATA_IMPORT_NOT_APPROVED` · `MASTER_DATA_IMPORT_ROW_INVALID` · `MASTER_DATA_MERGE_NOT_ALLOWED`

Use `masterDataErrorCodeForFailureDetails(details)` when adapting package failures to API/UI. Internal `details.reason` may retain narrower legacy reasons, but equivalent failures must map to one canonical `MASTER_DATA_*` code. Do not create aggregate-specific canonical names such as party-not-found, item-version-conflict, or warehouse-invalid-state.
